# GitEdge account runner signing migration plan

## Target and feasibility

Move the complete signing service into GitEdge's existing Actions Worker and account-runner platform. The final shape has no separately deployed `signing-center` Worker: GitEdge Actions owns signing submission/status/download APIs, source admission, product policy, request state, scheduling, credential authorization and artifact integrity; a user's system-managed private `Runner` repository supplies the approved signing profile/workflow, and a dedicated GitEdge account-runner pool executes it. GitHub build identity may remain solely as source provenance where a product policy requires it; signing execution and callbacks use only native GitEdge run/runner/lease identity.

**Feasible, but not a direct switch today.** GitEdge already registers/revokes namespace/repository-scoped account runners, schedules GitEdge workflow jobs against labels/capacity/budgets, issues a short-lived lease and scoped `ge_job_` credential, renews/cancels leases and records completion. Its current queues contain only ordinary GitEdge Actions runs and connected GitHub webhook/JIT jobs. The smallest coherent final implementation is to extend `workers/actions/` with the signing API/state/transfer and trusted-profile queue path, reuse the native scheduler and runner lifecycle, then remove the old `signing-center` deployment after drain and acceptance. Current gaps are protected signing-profile launch from the non-discovered path, source/workflow dual-identity tracking, signing-specific secret authorization, native runner attestation for callbacks, and large signing archive transfer. No live runner readiness or signing credentials were inspected.

The special `Runner` repository is one per human user in the existing `personal` namespace, fixed slug `runner`, owner-only and private. GitEdge keeps its system kind and repository identity attached to stable user/namespace IDs across username changes. It runs only its own personal push/manual workflows; existing project workflows stay in their current repositories and are not fanned into Runner. The owner may edit ordinary workflows, but signing profiles live under the separate, non-discovered `.gitedge/signing/<profile>.yml` path. A trusted GitEdge signing profile pins an immutable workflow commit; modifying that pinned definition requires profile re-approval/revision. Ordinary CI cannot claim signing capability or retrieve signing credentials. A trusted per-request signing process may receive the minimum short-lived credential material only on a dedicated signing host/VM or a host with a real OS identity/security boundary that ordinary CI cannot read or escalate across. A separate profile or label on a shared host is not isolation: the current broker launches jobs under the same service UID, so same-UID ordinary jobs can read host files regardless of restrictive file mode. Local key material is confined to a temporary keychain/file and cleaned after use within that isolation boundary. Same-repository jobs keep their repository-scoped token; cross-repository source access requires explicit authorization with auditable exact scopes. The source is a validated archive and is never checked out or executed by the signing job. Align provisioning, profile approval and lifecycle with the account-runner repository design before implementation.

## What exists in GitEdge

The surveyed GitEdge tree is baseline `7d5cdda82b97eb7accf46ac96ef326e98caa1fe9` (the current planning branch adds documentation only).

- `packages/contracts/src/runners.ts` defines runner registration scopes (namespace owner plus optional repository), runner labels, capacity/budget reports, claim and lease callback schemas. The capacity contract recognizes Linux/macOS/Windows and x64/ARM64, one slot, memory/disk/CPU/tools, and time/cost budgets.
- `workers/actions/src/runners.ts` registers a runner only for a namespace/repository the registering human owns/administers, stores a token hash, authenticates each machine request with that registration, atomically claims jobs, obtains a run-scoped `ge_job_` token from Auth, and validates the registered runner, lease token/hash, active status and expiry for heartbeat/completion. Runner tokens can be revoked. This machine API does not currently accept a signing request.
- `workers/actions/src/runner-scheduler.ts` queues and selects only `actions_runner_runs` and connected GitHub runner jobs, bounded by namespace/repository scope, labels, one busy job, capacity and budget. `workers/actions/src/index.ts` queues runner execution only for supported human push or workflow-dispatch actions; its public manual dispatch is not a signing-center machine principal.
- `scripts/runner-broker.mjs` receives GitEdge run metadata, verifies the `ge_job_` token shape, run/workflow/ref fields and broker profile scope, validates workflow demand against host capacity, runs a fresh per-job directory, heartbeats while executing, kills the child on cancellation and reports completion. `scripts/actions-runner.mjs` removes inherited GitEdge/GitHub token variables and maps the job-scoped credential into the Actions-compatible job secret context. The current design is per-process/per-run directory cleanup; it is not evidence of a disposable VM or OS-level sandbox for self-hosted signing. Current broker jobs share a service UID, so profile/label separation and file permissions do not prevent a normal workflow on the same host from reading files owned by that UID.
- GitEdge runner labels support general macOS, Windows and Linux hosts. Existing signing requirements are more specific: Windows x64 with the approved signing tool/profile, macOS with the required Apple toolchain, and iOS on macOS ARM64 with the required Xcode/iOS signing toolchain. The broker can route labels/capacity, but no current runner inventory or readiness was inspected. A dedicated signing pool must be checked on real hosts before cutover.
- GitEdge's own Action artifact capture is bounded to 24 MiB (`workers/actions/src/run.ts`): `MAX_ARCHIVE_BYTES` is 24 MiB, and the API publication path stores the captured archive in R2 after reading it from the Durable Object. Signing-center accepts archives up to 2 GB and streams them in 5–64 MiB parts (up to 10,000 parts) to its own transfer store. This 24 MiB generic Actions limit cannot carry current signing archives; move the bounded 2 GB multipart streaming path into GitEdge Actions without increasing the generic Actions cap, and retain whole-archive/per-output digest checks.

These facts support moving signing policy/state into the existing GitEdge Actions Worker and reusing its native scheduler/job lifecycle, not treating today's general queue as a signing service.

## Required trust and job contract

1. Provision exactly one system-managed `Runner` repository per human user in that user's `personal` namespace, with fixed slug `runner`, stable identity by user/namespace IDs, owner-only access and locked private visibility. Continue allowing ordinary workflows under `.github/workflows/`. Keep signing definitions under `.gitedge/signing/<profile>.yml`, outside normal workflow discovery; only an approved profile pinned to an immutable workflow commit makes one executable as a signing job. This is the smallest clear boundary for preventing a push or ordinary `workflow_dispatch` from accidentally launching a signing profile; using a normal workflow path would require equivalent denial checks at every trigger/dispatch path plus signature-specific permissions. A file's presence or normal workflow edit must never grant signing trust.
2. Add a narrowly scoped Actions-owned admission path for signing requests. Authenticate product callers under an explicit account/project grant. Accept only a signing request and validated source proof/artifact metadata; derive the profile, pinned commit, signing label, timeout and policy from GitEdge's protected signing configuration. Do not accept caller-selected runner, workflow body, labels, secret names or credentials. Reuse the existing Actions run/job and scheduler model where its data contract permits; add only signing metadata needed to bind the job to the request.
3. Bind admission to immutable workflow commit and locked Runner repository identity/private status. Store source repository/OID separately from signing workflow repository/OID in the native run record; the source repo is provenance/input, never the workflow checkout. Route to platform-specific dedicated labels/pools (`signing-windows-x64`, `signing-macos`, `signing-ios-arm64` as policy names), with one active signing job per host. Do not share signing-capable hosts or capabilities with ordinary personal workflow jobs. Preserve platform separation and existing host requirements.
4. Validate signing callbacks and credential operations inside GitEdge Actions against native run/runner/lease state. Bind stable user/namespace identity, private Runner repo ID, approved profile revision and immutable workflow commit, GitEdge run ID, registered runner ID, request/generation/nonce, source proof and active lease. GitHub executor run IDs, executor actor checks and GitHub OIDC are removed from execution authorization. Existing `ge_job_` is scoped for GitEdge APIs and is not by itself a signing grant; do not trust a caller-provided run ID string. Same-repository jobs retain their existing repository-scoped token; only explicitly authorized cross-repository source operations receive narrowly scoped, auditable resource access.
5. Keep durable key custody in Actions-owned encrypted service storage, inaccessible to ordinary workflows. A trusted signing tool running only on a dedicated host/VM or a host with a verified OS identity/security boundary may receive the minimum credential material for one request; if `codesign`/iOS tooling needs a local key, import it into an isolated temporary keychain/file and erase it on every exit path. Ordinary CI receives no signing credentials. Never store keys in Runner workflow files, D1 workflow/run records, broker-wide environment or logs. Current runner support does not establish host isolation, the signing credential channel or cleanup.
6. Keep platform verification and signing-specific large artifact handling in GitEdge Actions. The account runner uploads through an Actions signing transfer endpoint; Actions validates declared outputs, archive digest/size and platform verification report before marking the signing request successful. Generic Action completion is execution evidence, not proof that a signed artifact passed signing verification.

## Concrete changes by component

### GitEdge Actions (final signing service)

- `workers/actions/src/index.ts`, `workers/actions/src/runner-workflow.ts` and `packages/contracts/src/`: add signing submit/status/cancel/download contracts and routes in the existing Actions Worker. Port the center's source repository/build run/actor/ref/SHA, project allowlist, version/tag policy, idempotency, transfer mode/size and rate-limit checks. Use the existing GitHub source read integration/credentials at the smallest required scope; do not require GitHub identity for executor admission or callback. `execution_visibility` and `public_execution_allowed` disappear from the caller/API/policy contract.
- Move the signing request state machine and immutable policy snapshot from signing-center `src/native.ts`, `src/native-contracts.ts`, `src/execution-store.ts`, `src/store.ts` into Actions-owned records. Reuse existing `actions_runs`/`actions_runner_runs` for execution and lease lifecycle; add only one signing-request record for source policy, idempotency, artifact state and run binding. Distinguish source repository/OID from Runner workflow repository/OID, and bind stable user/namespace ID, private Runner repo ID, approved signing profile revision, GitEdge run/runner IDs and lease generation. Keep transitions under Actions-owned storage; stale leases, duplicate dispatch, cancellation and retries remain fail-closed.
- Move signing-center's R2 multipart transfer, request-bound source ingest, output allowlist, archive digest/size, per-file verification and download expiry into the existing GitEdge Actions Worker/bucket boundary. Current signing archive limits are up to 2 GB with 5–64 MiB multipart chunks and at most 10,000 parts; the generic Action artifact cap is 24 MiB. Add only a bounded signing transfer path and full digest checks; do not increase the generic Actions artifact cap. Source repository access is opt-in and exact-scope; the signing process receives only the validated archive and fixed policy inputs.
- Move source/build policy, Apple credential ownership, Windows profile selection and platform verification code into Actions-owned signing modules. GitEdge has encrypted secrets for other services but no Actions signing-secret store. Add only the Actions-owned protected storage needed for the existing signing profiles/credentials; ordinary personal workflows cannot read it. Do not persist keys in the special Runner repo or run records. The trusted signing process may obtain narrowly scoped, short-lived credential access for a single request. If an Apple tool requires a local key, import it only into a temporary isolated keychain and scrub it after the job; do not claim the key never reaches the host. Windows currently relies on GitHub OIDC to enter its Azure certificate profile; prefer Azure Workload Identity Federation only if GitEdge's issuer is verified and accepted by the Azure tenant, or use host managed identity limited to the approved remote signing API. GitEdge currently exposes neither identity to signing jobs, so validate the route with the Azure tenant before cutover; do not substitute a self-issued long-lived certificate path.
- Keep `workers/auth/src/index.ts` and runner-machine authentication/lease validation inside GitEdge as the authority for runner identity; Actions signing APIs must authorize the native run/runner/lease rather than accept self-asserted IDs. No new separately deployed signing Worker or permanent proxy service is needed.
- Keep the public Actions API surface under the GitEdge Gateway's existing Actions route family. Update caller endpoints/API credentials to GitEdge only when the new API and source checks are accepted. If a temporary transition adapter is needed, it routes to the new Actions implementation and is removed at cutover; there is no permanent signing-center runtime or backward-compatibility route.

### GitEdge Actions and runner broker

- `packages/contracts/src/runners.ts`: define the strict signing admission/attestation contract and platform-pool labels; do not widen generic workflow dispatch schemas to accept arbitrary signing credentials.
- `workers/actions/src/index.ts` / `workers/actions/src/runners.ts`: add the Actions-owned signing submission/admission path that creates a native signing run from the approved `.gitedge/signing/<profile>.yml` definition and attaches signing metadata. Check stable user/namespace identity, private Runner repo ID, approved profile revision/OID, bound source repository/OID, request idempotency and platform policy before enqueue. Existing `parseRunnerWorkflow` accepts only `.github/workflows/` paths, and the normal manual dispatch path is user-oriented; neither currently launches this non-discovered signing definition. Claim uses existing atomic assignment, capacity/budget, one-slot and lease behavior. Provide authenticated native run/runner/lease operations and cancellation/readback; reject replay, stale lease, wrong profile/source OID, wrong runner or wrong account.
- `workers/actions/src/runner-scheduler.ts`: choose signing execution class and pool from server-authorized profile/request state, not workflow-supplied labels. Bind the registered runner to the exact private Runner repository and approved platform pool; ordinary job claims cannot acquire signing class or signing credentials by asserting reserved labels. Keep one job per runner and fail closed on unknown/stale capacity.
- `scripts/runner-broker.mjs` / `scripts/actions-runner.mjs`: add a signing-only execution capability that accepts only the profile-approved immutable definition and source artifact binding; ordinary Actions workflow execution must never receive that capability or credential channel. Do not inject signing credentials into the generic `GITHUB_TOKEN`/`GITEDGE_TOKEN` secret context. Stop and scrub signing processes on lease invalidation; verify per-run keychain cleanup and no cross-job persistent key cache. Enforce a dedicated host/VM or OS security identity that ordinary CI cannot share or escalate into; the current same-UID broker model does not meet this condition, and `localmac`/`localwin` hosts that accept ordinary CI cannot hold signing material until isolated.
- `workers/auth/src/index.ts`: if signing needs a distinct job assertion, issue it only after native runner claim and bind it to the exact run, runner, protected workflow, request and lease expiry. Never make it an account-wide API token.
- Do not reuse the GitEdge GitHub webhook/JIT runner route for signing. It represents GitHub-controlled workflow jobs and preserves the GitHub execution identity that this migration removes.

### Callers and workflows

Keep the currently confirmed submitters in IRIS-Build, Epilogue and Oblivionis. Their release workflows continue to submit source run/build proof and source archive; `execution_visibility` is removed and the endpoint/credential moves to GitEdge Actions. Their project workflows remain in place and are not replaced by Runner. GitEdge Actions admits the source and queues the trusted signing profile on the user's special `Runner` repo. Signing jobs never check out or execute the untrusted source build repository; Actions supplies only the validated source archive and fixed policy inputs. If the source is cross-repository, admission requires an explicit grant with exact auditable read scope; same-repo jobs continue to use their repository-scoped token.

The `Runner` repo contains profile-pinned signing definitions outside ordinary workflow discovery; GitEdge provisioning and Actions-owned policy authorize the profile and server-selected execution class/pool. Each user's signing host is registered at repository scope for that user's locked private `Runner` repo and only the platform pool it is allowed to serve.

## Platform feasibility and explicit gaps

| Platform | Existing requirements/evidence | Migration requirement before canary |
| --- | --- | --- |
| Windows | Current executor requires Windows x64, Microsoft signing tooling and Azure certificate-profile login via GitHub OIDC. GitEdge broker recognizes Windows x64 and supports labeled self-hosted hosts. | Dedicated Windows x64 host/VM or verified isolated OS identity; verify GitEdge-issued Azure Workload Identity Federation or a host managed identity limited to the approved remote signing API; prove certificate ACL, timestamping and post-sign verification. |
| macOS | Current executor uses macOS tooling and credentials held by signing-center. GitEdge broker recognizes macOS hosts. | Dedicated macOS host/VM or verified isolated OS identity with exact build/sign/notarization toolchain; make trusted signing code—not ordinary CI—the only consumer of a request-bound short-lived credential; use per-run Keychain import/cleanup if local key material is required; preserve notarization and output identity checks. |
| iOS | Current executor requires macOS ARM64 and Xcode 27.1; signing-center stores iOS signing credentials separately. GitEdge broker supports macOS ARM64 labeling/capacity. | Dedicated macOS ARM64 host/VM or verified isolated OS identity with pinned Xcode/iOS SDK; trusted signing code only, per-request short-lived credentials and per-run provisioning/profile/keychain cleanup; keep team ID, provisioning profile, device and IPA verification checks. |

No current host inventory, installed toolchain, Azure federation trust or account runner deployment state was read. So all three platforms are scheduler-compatible in principle; production readiness remains an explicit pre-cutover validation, with Windows identity and signing-specific credential isolation the largest known gaps.

## Cutover and acceptance order

1. Implement/provision the per-user private `Runner` repository contract and verify stable identity/visibility locking, owner-only access, separate `.gitedge/signing/` profile path and profile revision approval. Create separate platform signing pools and verify their runner registrations, exact OS/architecture/tools and isolation. Do not add real signing secrets during development.
2. Port the old service's source/product policy and request state into GitEdge Actions. Add the Actions-owned submit/status/cancel/download API, signing-profile admission, lease-bound signing operation, service-owned encrypted credential storage and signing-only multipart data path. Reuse native `actions_runs`/`actions_runner_runs` for job identity and scheduling; do not maintain a second permanent signing queue or deployment. Add contract and authorization tests before attaching production credentials.
3. Test with non-production signing material across public and private source repositories. Verify invalid source identity/ref/SHA is rejected before queueing; changed Runner repo visibility/identity/workflow OID, wrong account, wrong runner, replayed nonce, expired/revoked lease, unauthorized signing operation and output digest/report mismatch all fail closed. Exercise GitEdge queue cancellation and retry reconciliation without running the same signing generation twice.
4. Run platform-specific canaries on dedicated real hosts using a non-production request/credential; compare the final artifact's input binding, signatures, platform verification report and Actions-recorded digests. Verify ordinary workflow logs and processes cannot read signing credentials, and verify cleanup of logs, artifact storage, temporary keychain/files and host caches.
5. Pause release submissions and drain every nonterminal request in signing-center. Preserve required historical request metadata and retained artifacts using the agreed retention procedure; do not clear or rewrite data before reconciliation. Update all confirmed callers to the GitEdge Actions endpoint and credentials; keep source GitHub proof and source archive behavior during the first canary wave. Run public-source and private-source canaries per product family plus one canary per enabled platform.
6. After caller readback, history/retention reconciliation and all canaries pass, disable the old signing-center API/Worker and retire the old GitHub executor workflows/tokens. Keep only the narrowly scoped GitHub source-read integration needed for provenance or explicit source-archive retrieval. Remove any temporary adapter in this cutover; no separate signing service, old API or execution fallback remains.

Stop before enabling production signing if the Runner repo identity/private lock or profile approval can be bypassed; Actions cannot verify native run/runner/lease identity; ordinary personal CI can claim signing capability, share signing host identity or access its credentials; a platform runner's OS isolation/toolchain is not demonstrated; Windows Workload Identity Federation/managed-identity signing has not been validated; source validation or explicit cross-repository authorization can be bypassed; history/retention cannot be reconciled; or artifact digests/platform reports fail. A failed canary leaves normal release submissions paused; repair forward inside GitEdge. Do not restore GitHub executor dispatch or keep the old signer as a fallback.
