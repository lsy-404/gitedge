# Private signing executor cutover plan

## Target

Keep the existing `signing-center` service and API. Route every new macOS, Windows and iOS signing request through the single private GitHub repository [`lsy-404/signing-exec-private`](https://github.com/lsy-404/signing-exec-private). Public source repositories remain eligible to submit requests when their current source-run, actor, workflow and project policy checks pass; the resulting job always executes in the private repository. Keep separate platform workflows and runners in that repository.

There is no public executor fallback after cutover. Remove the request-side `execution_visibility` selector (`auto|public|private`) and the project-side `public_execution_allowed` exception. Keep `source_transfer` (`push|pull`) because it selects how source bytes reach the center, independently of where signing runs. Keep `resolved_execution_visibility` only as historical status data if existing request rows require it; it must never drive dispatch or executor authorization.

## Product changes by repository

### `lsy-404/signing-center`

1. In `src/policy.ts`, remove `public_execution_allowed` from `projectSchema` and every project record. Remove `execution_visibility` from the public submission contract so the center no longer accepts a caller-selected executor lane. Preserve existing project ID, source repository, platform, source workflow, actor, required-job, source transfer, size, tag and daily-limit policy.
2. In `src/coordinator.ts`, remove visibility derivation from source repository privacy and remove the `public_execution_allowed` gate. Always take the private executor path for the requested platform. Preserve the current source validation: GitHub repository identity/admin state, run attempt 1, allowed actor/event, configured workflow path, required job, source ref/tag and exact SHA, push digest/size or pull artifact binding, source OIDC identity where required, idempotency and run-binding rules.
3. In `src/native.ts`, select only the private executor configuration for macOS, Windows and iOS. In `src/native-contracts.ts`, replace the `public`/`private` config split with one approved executor list per platform; remove snapshot visibility as an executor selector; require the selected GitHub repository ID to be the approved private repository and to report `private: true`. Keep exact workflow path, immutable ref, commit SHA and runner-token hash checks. Keep the existing executor list only for approved private revisions/rotation; every member must identify the same private repository. There must be no public repository entry or public execution code path.
4. Keep platform-specific configuration and policy digests: macOS Apple credential flow/notarization, Windows Azure profile and Authenticode checks, iOS Team ID/profile/device checks. Continue validating the request snapshot, nonce, runner token, run ID/attempt, actor, workflow path/ref/SHA, lease, input/output digest and verification report at each stage.
5. `src/admin-contract.ts`, `src/coordinator.ts` response projection and `ui/src/components/RequestsTable.vue` currently expose/display `resolved_execution_visibility`. Keep the Durable Object `requests.visibility` column as historical/request-status metadata: write `private` for every new row and preserve old row values for status history. Keep the response field only to expose that stored metadata; never use it for routing. If the UI keeps the column, label it as the execution repository privacy recorded for that request. Make sure stored historical request bodies containing the removed selector can still be summarized without weakening the new external request schema; this is a read-only persisted-record concern, not an API fallback.
6. Update README/API contract text and tests. Update `test/policy.test.ts`, `test/native-execution.test.ts`, `test/security.test.ts`, `test/org-release.test.ts`, `test/publication.test.ts`, `test/admin-contract.test.ts`, and relevant runner/client tests. Add behavioral assertions that (a) both public and private source repositories route to the same approved private executor, (b) the executor repo must be private and match the configured repository ID, and (c) no submitted field or configuration can select the public executor.
7. Replace current platform executor config files: `src/macos-executors.json`, `src/windows-executors.json`, `src/ios-executors.json`. Remove all entries for `lsy-404/signing-exec-public`; retain only verified `lsy-404/signing-exec-private` pins. Update the center's matching fixtures and any admin display/readiness assumptions. Keep center credentials/bindings in place; the API endpoint, API key ownership, Apple credential storage, R2 transfer and retention behavior do not change.

## Cutover order

1. **Preflight private target.** Read back private executor repo metadata and validate all candidate tag-to-SHA/workflow-path bindings. Check signing environment restrictions by tag name, private token presence by name only, Windows Azure OIDC trust, current Mac/iOS broker readiness and required tools. Run the private executor's established checks before any center edit. Make sure one approved private pin is available for each enabled platform.
2. **Update callers to the no-selector request contract.** Update the six caller scripts above and their tests, preserving their current source-run authorization and transfer shape. Leave workflow YAML and API-key permissions alone unless the implementation reveals a necessary environment wiring change. Validate all callers against a mocked center contract before deploying the stricter center contract.
3. **Freeze and drain old public executor work.** Pause new source workflow submissions at each caller. Use an authoritative center inventory of every nonterminal request, not just the recent dashboard page. Wait until all requests whose snapshot selects `signing-exec-public` are terminal and their runner callback windows are closed. If a request remains awaiting source, running, finalizing/notarizing, retryable or downloading under the old public snapshot, stop here; do not remove its pins/tokens. Preserve already-succeeded outputs under existing retention rules.
4. **Deploy single-private center contract and pins.** In one reviewed center release, remove the public lane, reject the removed caller selector under the strict submission schema, select private configs unconditionally, and update per-platform pins to verified private tags/SHA. Keep source repository and source workflow authorization independent of execution repository privacy. Once this release is live, confirm readiness for macOS, Windows and iOS and read back that no public executor config remains.
5. **Run controlled acceptance per platform and source visibility.** Exercise a public-source macOS request, a private-source macOS request, Windows and iOS through the private workflows; use the existing source request protocol and approved test/release fixtures. For each, verify the center-selected executor repository and workflow run identity, successful full input/output digest checks, platform verification report, and final status/download result. Confirm a public-source request succeeds through the private repo and a request with invalid source actor/ref/SHA is rejected before signing authorization. Do not count readiness or host smoke as proof of a completed signing artifact.
6. **Retire public executor credentials and workflow access.** Only after the drain and successful acceptance, remove all public executor refs from center config (done in step 4), disable public repo signing workflows/environment dispatch eligibility, and revoke its runner token(s) so a manually dispatched stale job cannot authenticate. Read back that no center route/config accepts `lsy-404/signing-exec-public`. Keep the public repository available for audit until its owner separately chooses archival/deletion; this cutover does not delete repositories.
7. **Resume source submissions.** Unfreeze callers only after the readbacks and acceptance above pass. Record the center deployment revision, private workflow refs/SHAs, canary request IDs, final status and output digest in the signing-center audit record. Do not record secret values or hashes in the cutover notes.

## Verification and stop criteria

Run in `signing-center` after implementation:

- `pnpm run check`
- `pnpm test` (especially the contract/security suites listed above)
- `pnpm run build` (Worker/UI build and dry-run)
- `pnpm exec wrangler deploy --dry-run` for the production config, without deploying as part of verification

Run in `signing-exec-private`:

- `node --check runner/client.mjs`
- `pnpm --dir runner install --frozen-lockfile --ignore-scripts`
- `node --test test/macos-runner.test.mjs`
- workflow syntax validation with the repository's available actionlint/check workflow
- actual host checks through the existing platform workflows; Windows and iOS must run on their self-hosted labels.

Run the relevant caller tests in IRIS-Build, Epilogue and Oblivionis; assert the request body contains no `execution_visibility` and still includes all required source fields and stable idempotency identity. Follow with one real end-to-end signed artifact per enabled platform before opening normal source submissions.

Stop before center deployment or public token retirement if any old public request is nonterminal; a private tag/SHA/workflow/runner check fails; any private runner token or required environment is missing; Windows OIDC resolves outside the approved certificate profile; an iOS/macOS identity or host prerequisite differs from current pinned policy; an invalid source actor/ref/SHA is accepted; or any output digest/report does not match the submitted source and frozen policy. On a canary failure, keep release submissions frozen and repair forward in the private path. Do not restore public executor routing as a fallback.
