# API endpoints

Responses use `{ "data": ... }`; failures use `{ "error": { "code": ..., "message": ... } }`. Private repository existence is hidden from unauthorized readers.

Gateway: `GET /api/health` (anonymous, per-IP rate limited) returns `{ status: "ok" | "degraded", services: { <name>: { ok, latencyMs } } }` for `auth`, `forge`, `git`, `deploy`, `actions`, `limits` and `d1`, with HTTP 503 when any probe fails. Rate-limited requests receive 429 with a `Retry-After` header and `retryAfter` seconds in the body.

Auth: register, login, logout, session and identity-only GitHub OAuth under `/api/auth`. Account agent CRUD lives at `/api/auth/agents`; each agent's session collection lives at `/api/auth/agents/:id/sessions`. Sessions return API/Git credentials once. Account Git credentials live at `/api/auth/tokens`. Personal access tokens live at `/api/auth/access-tokens` (`GET` lists, `POST` creates, `DELETE /:id` revokes). Creation takes `{ name, scopes, expiresInDays (1-365), repositoryIds? }` and returns the `gep_` plaintext once; it requires a signed-in browser session that confirmed its identity in the last 10 minutes (otherwise 403 `reauth_required`) and is refused for Bearer tokens and agent sessions. A token is accepted as `Authorization: Bearer gep_...` on `/api/*` and as the HTTP Basic password (any username) on Git Smart HTTP. Scopes: `repo:read`, `repo:write` (implies read), `issues:write`, `pulls:write` (both imply repository read), `org:read` and `admin` (all). Services answer `403 insufficient_scope` when a request needs a scope the token lacks, and tokens limited to `repositoryIds` cannot reach other repositories. Invalid, revoked or expired tokens receive 401. SSO provider discovery, login, metadata, identity linking and single sign-out live under `/api/auth/sso`; see [SSO configuration](sso.md). Signing keys are listed, added and revoked at `/api/auth/signing-keys` (with `/signing-keys/challenges`); `/api/auth/profile` and `/api/auth/agent-profiles/:owner/:handle` expose profiles.

Account security (Auth, browser sessions only): `POST /api/auth/login` returns either the user or `{ secondFactorRequired, mfaToken, methods }`; finish with `POST /login/second-factor` (`/login/second-factor/options` prepares a passkey prompt). Passkey sign-in is `POST /login/passkey/options` then `/login/passkey`. Recovery: `GET /recovery/options`, `POST /recovery/password` (username and recovery code), `POST /recovery/email` (always 202) and `POST /recovery/email/confirm`; `POST /email/verify` spends a verification link. Signed-in management lives under `GET /security` (summary), `POST /reauth` and `/reauth/passkey/options` (confirm identity for 10 minutes), `POST /security/password`, `PUT|DELETE /security/email`, `POST /security/totp`, `/security/totp/confirm`, `/security/totp/disable`, `POST /security/recovery-codes` and `/security/passkeys[/options]` with `PATCH|DELETE /security/passkeys/:id`. Sensitive routes answer 403 `reauth_required` outside the confirmation window. See [account security](account-security.md).

Forge: `GET /api/forge/usage` returns the caller's repository count, storage use (`usedBytes` is `null` because Artifacts does not report repository size) and the limits of their user group. Creating a repository beyond the group limit returns 403 `quota_exceeded` with `error.quota` `{ resource, used, limit }`. `/api/forge/repositories`, `/repositories/by-name/:owner/:repo`, and organization/member management. Repository resources are `/repositories/:id/issues`, `/pull-requests`, `/discussions`, `/wiki`, `/settings`, `/tasks`, `/memory` (404 `feature_disabled` when tasks are off), `/assignee-candidates`, `/branch-rules` `/collaborators`, `/invitations`, `/audit-log` and `/releases`. Numbered items expose details, PATCH and comments. PRs expose `diff`, `reviews`, `checks` and `merge`; merge requires expected base/head OIDs. Line comments live under `/pull-requests/:n/review-comments`: `GET` lists them (anonymous on public repositories; `truncated` is set past 1000), `POST` creates a thread `{ body, commitOid, path, side: LEFT|RIGHT, line, startLine?, diffHunk?, pending? }` (the commit must be the current head, otherwise 409 `stale_commit`) or a reply `{ body, inReplyTo, pending? }` (replies always attach to the thread root), `PATCH /:id` edits (author) and `DELETE /:id` removes (author or member; deleting a thread root removes its replies, so a non-member author gets 409 `thread_has_replies` while replies by others exist), and `POST /:id/resolve` / `POST /:id/unresolve` toggle the thread (thread author, human pull request author or human write member). Each comment carries `outdated`, true when its `commitOid` differs from the current head (the stored original `diffHunk` stays available). `pending: true` comments are visible only to their author until the next `POST /reviews` by the same identity publishes them together with the verdict. Published line comments and edits notify newly mentioned users (`mentioned`) and agents; mentions in pending comments are delivered when the review publishes them. All of these need the `pulls:write` scope and a writable agent session. `GET /issues/:n/references` returns the pull requests that mention or close the issue and its `closed_by_pull_request` events (`truncated` is set past 100 of either). Closing keywords (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, case-insensitive, followed by `#n` or same-repository `owner/repo#n`) in the title, body or commit messages of a pull request merged into the default branch close those issues in the same D1 batch as the merge. A branch rule with `requireConversationResolution` rejects merges with 409 `threads_unresolved` while any published thread is unresolved. Wiki pages expose history and revision-aware PUT/restore.

Notifications (Forge, signed-in users and personal access tokens with `repo:read`; agent sessions are refused): `GET /api/forge/notifications` lists the caller's notifications newest first with `unread=true`, `repositoryId`, `reason` (`assigned`, `review_requested`, `mentioned`, `comment`, `check_failed`, `merged`, `invited`), `limit` (1-50, default 25) and the `before` cursor from the previous `nextCursor`. Each item has `reason`, `subjectKind`, `subjectNumber`, `title`, `repository`, `actor`, `createdAt` and `readAt`. Items for repositories the caller can no longer read are omitted. There is one notification per user and thread; new activity updates its reason and marks it unread again. `GET /notifications/unread-count` returns `{ unread, capped }` (counted up to 100). `POST /notifications/read` takes `{ ids }` (at most 100) or `{ all: true, repositoryId? }` and returns `{ updated }`. `GET` and `PUT /notification-preferences` read and replace `{ mutedReasons }` (tokens need `admin` to replace them); muted reasons stop new notifications only. A repository invitation addressed to an existing user notifies them (`invited`) when it is created; while it is pending the invitee sees it even for a private repository, and it disappears again if the invitation is cancelled, declined or expires without granting access. Organization invitations and link invitations do not notify, and later role changes do not either. Read notifications are deleted after 90 days.

Repository webhooks (Forge, repository administrators only; tokens need the `admin` scope; agent sessions are refused): `GET`/`POST /api/forge/repositories/:id/webhooks`, `GET`/`PATCH`/`DELETE /webhooks/:hookId`, `POST /webhooks/:hookId/ping`, `GET /webhooks/:hookId/deliveries`, `GET /webhooks/:hookId/deliveries/:deliveryId` (includes the payload) and `POST /webhooks/:hookId/deliveries/:deliveryId/redeliveries`. Creating, updating and deleting require a browser session that confirmed its identity in the last 10 minutes (403 `reauth_required` otherwise). `POST` takes `{ url, contentType: "json", events, active, secret? }`; the URL must be HTTPS on port 443, a public DNS name that resolves only to public addresses (400 `invalid_webhook_url` otherwise). A generated secret is returned once as `secret`; supplied secrets (16-128 characters) and later reads return `secret: null`, and `PATCH` with `rotateSecret: true` generates a new one. At most 20 webhooks per repository (409 `webhook_limit`); 503 when `WEBHOOK_ENCRYPTION_KEY` is missing. Events: `push`, `issues`, `issue_comment`, `pull_request`, `pull_request_review`, `check_run`, `release` (sent once when a release is published), plus `ping` for tests. Requests are `POST` with `Content-Type: application/json`, `X-GitEdge-Event`, `X-GitEdge-Delivery` and `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the body>`. A 2xx response succeeds; anything else (redirects are not followed, responses over 4 KB fail) is retried after 1, 2, 4 and 8 minutes, five attempts in total, then marked failed. Push payloads list one delivery per ref update that receive-pack reported as accepted (at most 20 per push; `before`/`after` are all zeros for creation and deletion) and carry no commit list. Delivery bodies clip text fields at 8 KB.

Lifecycle: repository deletion, purge-now, transfer and organization deletion require a browser session that confirmed its identity in the last 10 minutes and otherwise answer 403 `reauth_required`; tokens and agent sessions cannot perform them. `DELETE /api/forge/repositories/:id` soft-deletes a repository (repository administrators; body `{ "confirm": "owner/name" }`). A deleted repository answers 404 on every route, listing, profile and Git transport path, its name is released and its agent sessions are revoked (the response flags `revocationIncomplete` when Auth could not finish; the purge retries). Until it is purged it still counts toward the creator's repository limit. It stays restorable for 7 days: `GET /deleted-repositories` lists the viewer's recently deleted repositories, `POST /deleted-repositories/:id/restore` restores one (409 if the name was reused), and `DELETE /deleted-repositories/:id` (same confirmation) purges immediately. A scheduled Forge job purges expired repositories: it revokes agent sessions through Auth, deletes the Artifacts repositories and session forks through Git, then removes the D1 rows, persisting progress in `purge_state` and the fork cursor in `purge_cursor`; a failed attempt waits an hour (`purge_retry_at`) so it cannot starve other expired repositories. `POST /repositories/:id/transfer` (`{ "owner", "confirm" }`) moves a repository from a namespace the caller owns to their own account or an organization they own; the old path keeps redirecting (web routes and Git remotes answer 308), explicit collaborators are kept, inherited access follows the new owner and agent sessions are revoked. `DELETE /organizations/:slug` (owner only, body `{ "confirm": "slug" }`) is refused with 409 `organization_not_empty` while the organization holds any repository row, including deleted ones awaiting purge.

Repository import: `POST /api/forge/repository-imports` with `sourceUrl`, `owner`, `slug`, `visibility` and `description` queues an import of a public https Git remote through the native Artifacts import and returns `202` with the job. `GET /repository-imports` lists the caller's unfinished jobs, `GET /repository-imports/:id` returns one job (`queued`, `running`, `succeeded` or `failed`, with `progress` `starting`/`importing` and `errorCode`) and advances it, and `POST /repository-imports/:id/retry` requeues a failed job. Poll the job until it is terminal: Artifacts may keep copying after it accepts the import, and the repository record exists only after the copy is ready and its initial token is revoked. Jobs are visible only to their creator, and an active import reserves its repository name. Sources must be https on the default port with a DNS hostname whose A/AAAA records are all public: IP literals, local names and embedded credentials are rejected with `422`, and hosts resolving to private, loopback, link-local or reserved ranges fail the job with `invalid_url`. Starts and retries are limited to 5 per minute per user. Personal access tokens need `repo:write` to start or retry an import and `repo:read` to read jobs or `GET /usage`.

Git: `/api/git/repositories/:id/refs`, `tree`, `file`, `raw`, `commits`, `graph`, `compare`, `tags` and `archive`. Reads accept appropriate `ref`, `path`, `offset` or `limit` queries. Comparisons accept `base`, `head` and a validated `headSessionId`. Agent sessions operate on their own workspace by default.

Tags: `GET /api/git/repositories/:id/tags` lists up to 100 tags (natural order, newest name first) with `{ name, oid, commitOid, annotated, subject, timestamp }` and `truncated`; `?name=` returns one tag. `POST` takes `{ name, target, source?, message? }` where `target` is a branch name (the tag points at its tip) or a full commit id contained in `source` (default: the default branch); a `message` makes the tag annotated. `DELETE` takes `{ name, expectedOid }`. Both need repository write access (`repo:write` for tokens), refuse archived repositories and agent sessions, and answer 409 `tag_exists` or `refs_changed` on conflicts. Branch protection rules match branch names only, so tags need write access and nothing more. Creating a tag clones the source branch into memory and shares the Git service's 24 MiB transfer limit (413 `operation_limit` beyond it).

Raw files: `GET /:owner/:repo/raw/:ref/:path` (also `HEAD`) is served by the Gateway from the Git API (`/api/git/repositories/:id/raw?spec=<ref>/<path>` or `?ref=&path=`). The ref may contain slashes (the longest matching branch or tag wins) and may be a commit id or `HEAD`. Text renders inline as `text/plain`, images (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, SVG) inline with their own type, and everything else downloads as `application/octet-stream`; `?download=1` always downloads. Every response carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` and an `ETag` equal to the blob id (`If-None-Match` answers 304). Public repositories send `Cache-Control: public` (`max-age=300` when the ref is a commit id, otherwise revalidate every time); private repositories send `private, no-store` and answer 404 to readers without access. Files above 64 MiB answer 413 `file_too_large`.

Source archives: `GET /:owner/:repo/archive/:ref.zip` and `.tar.gz` (Git API: `archive?ref=&format=zip|tar.gz`) stream the tree of a branch, tag or commit under a single `<repo>-<ref>/` folder; symlinks and executable bits are kept and submodule links are omitted. The tree is walked before streaming: more than 5,000 files, 1,000 directories or 64 levels answers 413 `archive_too_large`, and unsafe paths answer 422 `archive_invalid`. Byte limits (128 MiB uncompressed, 32 MiB per file) are enforced while streaming, so exceeding one aborts the transfer instead of ending a valid but incomplete archive. `ETag` is the commit id plus format. Because an archive reads every tree and blob from Artifacts, the Gateway allows 10 archive requests per minute per user (per IP address for anonymous readers) on both URLs, on top of the normal request limits, and answers 429 with `Retry-After` beyond that.

Releases: `GET /api/forge/repositories/:id/releases` lists up to 100 releases (`truncated` flags more), `GET .../releases/latest` returns the newest published non-pre-release (404 when none) and `GET .../releases/:releaseId` one release; anonymous readers can read public repositories, and drafts are visible to members with write access only. `POST` takes `{ tagName, target?, source?, title?, body?, draft?, prerelease? }`: publishing creates the tag from `target` through the Git service when it does not exist (an existing tag is reused as it is and the release's `target` is then `null`; a missing tag without `target` answers 400 `tag_missing`), while a draft creates the tag when it is published. `PATCH` updates `title`, `body`, `prerelease` and `draft` (the tag name is fixed); a publish or unpublish that races another one answers 409 `release_changed`, so each publication emits one event. `DELETE` removes the release and its assets but keeps the tag. Writes need repository write access (`repo:write` for tokens), exclude agent sessions, and deleting a release from a browser session requires a recent identity confirmation (403 `reauth_required`). A repository holds at most 1,000 releases.

Release assets are stored in the `RELEASE_ASSETS` R2 bucket bound to Forge. `PUT .../releases/:releaseId/assets?name=<file>` streams the raw request body straight to R2: send `Content-Length` (411 `length_required` otherwise) and optionally `Content-Type`. Files are limited to 100 MiB (413 `asset_too_large`, checked before the body is read), a release holds 50 assets and a repository 10 GiB (409 `asset_limit` or `storage_limit`); names must be unique within a release (409 `asset_exists`) and a body that does not match `Content-Length` is rejected and removed. `GET .../releases/:releaseId/assets/:assetId` downloads with `Content-Disposition: attachment`, `nosniff` and a sandbox CSP and follows the repository's read access; `DELETE` removes one asset. Deleting a release or purging a repository deletes the stored objects. Release changes emit `release.published`, `release.updated` and `release.deleted` events (`ReleaseEvent` in `packages/contracts/src/releases.ts`) through `emitReleaseEvent`; handlers registered with `onReleaseEvent` in the Forge worker receive them. Publishing (directly or by turning a draft into a release) also queues a `release` repository webhook with `action: "published"` and records `release.published` in the audit log.

Code navigation (Git, all `repo:read` and 404 for unauthorized private readers):

- `GET /files?ref=` returns `{ oid, paths, truncated }`, every blob path of the commit sorted, bounded to 20,000 paths and 500 directories; `truncated` reports a partial list.
- `GET /history?ref=&path=[&cursor=]` returns `{ commits, inspected, truncated, nextCursor }`: first-parent commits that changed the file or directory, newest first. A request inspects at most 200 commits, returns at most 30 matches and stops at a tree-read budget; pass `nextCursor` as `cursor` to continue. Side-branch commits appear as their merge commit.
- `GET /blame?ref=&path=` returns `{ oid, path, blobOid, lineCount, hunks, commits, inspected, partial }`. Hunks are consecutive lines from one commit (`commitOid` is `null` for lines older than the inspected history, with `partial: true`). Walks the first-parent chain up to 500 commits, 150 file versions (8 MiB of earlier versions) and a fixed line-diff work budget. Binary files answer 422 `binary_file` and files over 512 KiB answer 422 `file_too_large`.
- `GET /commit-diff?oid=` returns `{ commit, files, truncated }`: the commit against its first parent (or the empty tree), at most 200 files and 2 MB of patches.

Responses addressed by a 40-character commit id (`files`, `blame`, the `history` cursor and `commit-diff`) carry `Cache-Control: public, max-age=3600, immutable` for public repositories and `private, max-age=3600` with `Vary: Cookie, Authorization` for private repositories and agent workspaces; branch and tag refs are `no-store`.

Git writes (require `repo:write`, repository write access, online editing enabled and a non-archived repository; protected branches reject direct commits with 403 and require a new branch):

- `POST /api/git/repositories/:id/edit` commits one UTF-8 text file (JSON: `branch`, optional `newBranch`, `expectedOid`, `path`, `content` or `null` to delete, `message`).
- `POST /api/git/repositories/:id/commit` commits several changes atomically. The body is `multipart/form-data` with a `manifest` JSON field (`branch`, optional `newBranch`, `expectedOid`, `message`, `changes`) and one binary-safe file field per `put` change. A change is `{ "op": "put", "path", "part" }` (adds or replaces the file in the field named `part`), `{ "op": "delete", "path" }` (file or directory) or `{ "op": "move", "from", "to" }` (file or directory; the destination must not exist). A file move may add `part` to replace the content while keeping the file mode. Changes must not overlap, paths cannot be empty, absolute, contain `..`, `.`, backslashes, control characters or `.git` components (including `git~1` and variants with trailing dots, spaces or ignorable Unicode), and are limited to 32 levels. With an agent session, the commit is written to that session's workspace.
- Limits: 100 changes, 5 MiB per file, 10 MiB of file content per commit (413 `file_too_large` / `payload_too_large`). The commit succeeds only if the branch still points at `expectedOid` (409 `refs_changed` otherwise) and the ref update is a non-force push. Commits made on the web are unsigned, so branches whose rules require signed commits are only reachable through a pull request from a new branch.
- Both endpoints return `{ data: { oid, branch } }` (`edit` also echoes `path`).

AI pull request summaries (Forge): `GET /api/forge/repositories/:id/pull-requests/:number/ai-summary` returns `{ unavailable, summary, job }`. `unavailable` is `site_disabled`, `repository_disabled` or `private_consent_required` when the feature is off (then `summary` and `job` are `null`). `summary` is the newest summary `{ id, author: { kind: "system", name }, headOid, model, content: { overview, notableChanges, riskAreas, reviewerFocus }, truncated, generatedAt }` and `job` the queued, running or failed attempt after it (`errorCode`: `disabled`, `diff_unavailable`, `rate_limited`, `model_error`, `invalid_output` or `timeout`). Anyone who can read the repository can read it. `POST` on the same path regenerates the summary of the current head and answers 202 with the same body; it needs a human member with write access, an open pull request and a non-archived repository, and answers 409 `ai_summary_unavailable` when the feature is off or 429 `rate_limited` with `Retry-After` at the hourly per-repository limit. Summaries are a separate system record: they never appear among reviews or comments and never count toward approvals. Repository settings carry `aiSummariesEnabled`, `aiSummariesPrivateConsent` and the read-only `aiSummariesAvailable`; enabling summaries on a private repository without consent answers 400 `private_consent_required`.

Actions: `/api/actions/repositories/:id[/...]`, `/api/actions/runs/:id` and `/api/actions/runs/:id/cancel`. Starting a run beyond six per repository per hour returns 429 `run_limit` with a `Retry-After` header.

Deploy: `/api/deploy/plan`, `session`, `account`, `resources`, `provision`, `migrate` and `deploy`. See [the deployment manifest](deploy.md) for source and permission requirements.

Invitations (Forge): collaborators and organization members join only by accepting an invitation; the earlier direct-add routes are gone. `POST /api/forge/repositories/:id/invitations` (repository administrators) and `POST /api/forge/organizations/:slug/invitations` (owners) take `{ "identifier" | "email", "role" }`. A username invitation is bound to that user and appears in their dashboard; an email invitation returns a one-time `token` (shown once, only its hash is stored) that the inviter sends as `https://<host>/invite#<token>`, so the invitee can register or sign in first and then accept. The invite page moves the token from the address into tab storage, so sign-in and registration return addresses never carry it. Invitations expire after 7 days, each target holds at most 50 pending ones, a repository holds at most 80 explicit collaborators (409 `member_limit` when inviting or accepting beyond it), `GET .../invitations` lists them and `DELETE .../invitations/:invitationId` cancels one. Invitees use `GET /api/forge/invitations` and `POST /invitations/:id/accept|decline` (bound to the invited user; anyone else gets 404), or `POST /invitations/lookup|accept|decline` with `{ "token" }`. Accepted invitations grant the role atomically; closed, cancelled and expired ones answer 409 `invitation_closed`. Existing explicit collaborators change role with `PATCH /repositories/:id/collaborators/:userId` and organization members with `PATCH /organizations/:slug/members/:identifier`. Personal access tokens need the `admin` scope for these writes, and tokens restricted to specific repositories cannot use the account-level invitation routes.

Audit log: `audit_events` is append-only (database triggers reject updates and deletes). Events are recorded for visibility changes, renames, archive changes, repository delete, restore, purge request and transfer, branch rules, collaborator and member changes, invitations, merges, agent webhook changes, repository webhook creation and deletion (the URL host only), release publication, access token create and revoke, authenticator, passkey, recovery code and password changes, account export and deletion, and site administration. Each entry stores the actor (user, agent with its session, or personal access token with its id), target, repository or organization and bounded metadata; credential-like keys and values are dropped before storage. `GET /api/forge/repositories/:id/audit-log` (repository administrators), `GET /api/forge/organizations/:slug/audit-log` (owners) and `GET /api/auth/audit-log` (the signed-in user's own security events) return `{ events, nextCursor }` newest first; pass `cursor` and `limit` (at most 100) to page.

Site administration (Auth, browser sessions of site administrators only; tokens and agents get 403): `GET /api/auth/admin/users?q=&cursor=`, `/admin/repositories`, `/admin/groups` and `/admin/stats` read; `POST /admin/users/:id/disable|enable` and `PATCH /admin/users/:id` (`groupKey`, `siteAdmin`) mutate and need a confirmation from the last 10 minutes (403 `reauth_required`). Site administrators cannot be disabled (409) until their stored flag is removed, and administrators named in `SITE_ADMINS` cannot be disabled at all. Disabling ends the user's browser sessions and revokes their agent sessions; the response flags `revocationIncomplete` when an agent session could not be revoked yet. A disabled account is rejected wherever Auth validates credentials: browser sessions, personal access tokens, agent sessions, Git credentials, password, passkey, GitHub and SSO sign-in (403 `account_disabled` at sign-in).

Account data (Auth, browser sessions with a recent confirmation): `GET /api/auth/account/export` streams a JSON archive with the profile, organizations, repository metadata, and the issues, pull requests, discussions, comments and reviews the user wrote, plus access token, Git credential and agent metadata without hashes. Each collection is capped at 2000 entries and the final `truncated` array names any that were cut. `POST /api/auth/account/delete` takes `{ "confirm": "<username>" }`; it answers 409 `organization_ownership` while the user is the only owner of an organization that has other members or repositories. Deletion revokes sessions, tokens, credentials and the user's agent sessions as well as every agent session on the user's personal repositories (503 with nothing changed when Artifacts cannot revoke one yet), cancels pending invitations, removes memberships, deletes organizations the user alone belongs to that hold no repositories, and soft-deletes repositories in the personal namespace for immediate purge; personal repositories already awaiting purge lose their restore window. The username stays reserved.
