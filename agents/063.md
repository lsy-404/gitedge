# Git authentication and access-token delivery

## Scope and decisions
- The user asked whether Git authentication can use a browser like GitHub, and requested permanent personal access tokens.
- The user subsequently explicitly requested implementing browser login together with permanent tokens.
- Implement Generic OAuth authorization for the fixed public GCM client using a maintained server library, S256 PKCE, strict loopback redirects, one-use codes, scoped short-lived credentials and refresh rotation. Reuse the existing browser session, consent, recent-authentication and token revocation controls.
- GCM 2.6.1 supports Generic OAuth through host-specific Git configuration. GitEdge currently accepts PATs over HTTP Basic and has inbound identity-provider login, but does not expose the OAuth authorization/token endpoints required by GCM.
- A browser integration requires an authorization-code flow with PKCE, registered loopback redirects, consent, one-use expiring authorization codes, and revocable scoped credentials. Existing OAuth client libraries do not implement an authorization server.
- Preserve unrelated modifications in the original checkout. Integrate the isolated implementation into the existing clean main worktree and push only the requested changes after verification.
