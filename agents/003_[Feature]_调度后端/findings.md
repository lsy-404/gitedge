# Findings

- The approved design is `docs/runner-scheduling.md` from commit `5697d93`; it fixes `need-*` semantics, a 512 MB default, relative cost, 24-hour minutes, 120-second peer deferral aging, and failure isolation at 3 attempts.
- The task worktree starts at `4d44da9`, clean, on `codex/runner-backend`.
- GitEdge and GitHub jobs are stored in separate D1 tables. Claim must continue checking both tables for the runner's active slot.
- The broker and Worker need one pure JavaScript scheduler module with a matching `.d.mts`; Worker contracts remain Zod schemas in TypeScript.
- Shared contracts/parser were committed as `098640df96bde2446a5dd16676acfc1d435e9d5e`; history cursor contract was refined in `949146623c641801697cb8f1651a80eee8276d4b` to use an opaque string cursor so rows with equal timestamps are not lost.
- Backend schema and integration are in `migrations/0047_runner_scheduling.sql` and `workers/actions/src/runner-scheduler.ts`. Claim uses a combined, ordered 25-row candidate set, checks current claimant capacity (old empty-body brokers have unknown capacity), records per-job deferral reasons, compares fresh idle peers, and atomically claims across both job tables with a one-slot guard and a compare-and-set on the runner report/budget snapshot.
- Capacity reports and budgets are schema-validated and retained; the claimant's capacity is only trusted for the current request. Existing capacity snapshots are used for peer scoring only. Empty legacy polls therefore cannot reuse an earlier capacity report to claim a job with explicit `need-*` requirements.
- Daily-minute usage is calculated from overlapping execution intervals clipped to the rolling 24-hour window across both GitEdge and GitHub queues. GitEdge claim deadlines are clamped to the smaller of the workflow timeout and parsed claim minutes. GitHub claim responses pass parsed minutes to the broker for its local deadline.
- Failure isolation applies to infrastructure failures (credential issuance, GitHub JIT/lease failures, and expired GitEdge leases), not workflow conclusions. Successful completion of any conclusion resets the streak. The third consecutive failure starts a 10-minute hold, then durations double with a one-hour cap; the exponent is bounded to avoid SQLite shift overflow.
- Cron removes at most 500 expired samples and stale deferrals per sweep. Deferrals retain per-runner reason-code snapshots until the job leaves the queue.
- Dashboard overview/history handlers and account UI are a separate agent's commits; route wiring and final combined integration are owned by the parent. This backend branch intentionally does not include that UI slice.
- The GH worker test exercises a 630 MB runner being rejected for a 4 GB claim, an empty legacy poll not reusing a prior 8 GB report, daily-budget rejection, capable-runner claim with original labels retained, normal completion reset, expired-heartbeat accounting, first hold duration and long-streak cap. A second D1 test case proves combined FIFO order, one active slot under concurrent cross-queue claims, and 24-hour overlap accounting (12 hours GitEdge + 1 hour GitHub = 780 minutes). Unit coverage includes parser behavior, hard constraints, scoring, and peer aging.
