## Credential and migration boundary

- Legacy Worker `voidcarve-signing-center` binds the `SigningCoordinator` Durable Object, `voidcarve-signing-credentials` R2 bucket and `voidcarve-signing-artifacts` R2 bucket. There is no KV or D1 binding.
- Legacy Apple credentials are AES-GCM ciphertext at `apple/signing-credentials.v1` and `apple/ios-signing-credentials.v1`, using `APPLE_CREDENTIAL_ENCRYPTION_KEY`. The old Worker can decrypt them in-process. Cloudflare secret metadata can confirm secret names and types, but Cloudflare does not return secret values.
- Legacy GitHub runner credentials and request state live in Durable Object SQLite. The GitHub source token is encrypted under `CREDENTIAL_ENCRYPTION_KEY`; executor repository signing secrets remain in GitHub Actions secret stores and are not readable back.
- GitEdge's existing credential write contract requires a recent-authenticated owner session and a currently approved immutable profile. Do not inject D1 rows or impersonate `approved_by`.
- Minimal viable migration: extend the existing owner-facing credential POST body with an `importLegacy` operation, keeping its existing authenticated-user and `recentHuman(user)` gate. GitEdge Actions generates an ephemeral recipient key pair in memory, calls a new `WorkerEntrypoint` RPC method on the legacy Worker over a private service binding, decrypts the returned envelope in memory, validates the existing platform schema and writes via `installSigningCredentials`. The RPC method accepts only fixed credential kinds (`macos`, `ios`, `github-source`) and a recipient public key; it reads the fixed R2 key or the existing `GITHUB_TOKEN` binding, encrypts the value to that recipient and returns only the envelope. No user receives the plaintext, no arbitrary object selector exists, the single-use private key is never persisted, the existing API writes the authenticated owner as `approved_by`, and the normal per-profile AES-GCM encryption remains in use. The source token can be imported separately against each approved profile revision using the same existing write path.
- Cloudflare documents that RPC methods are reachable through an explicitly declared service binding rather than a public URL, and that Workers can be isolated from the public Internet when only called through a binding. The legacy `WorkerEntrypoint` RPC adds no public export route. The new GitEdge route remains the already existing, recent-authenticated credential write path.
- Use a preview version only to inspect/upload code and verify deployment metadata. Cloudflare Version URLs use the Worker's existing bindings/resources, so do not invoke a migration operation against production from a preview URL. Exercise RPC and cryptography with a stub binding and synthetic ciphertext; do not fetch or log production credential objects during preview validation.
- This still requires changes to both Worker sources and the GitEdge Actions service-binding config. It must not be deployed until the parent reviews the RPC method, fixed-source mapping, per-profile write semantics and traffic-routing plan.
- The Azure `client_secret` is not part of old static policy and cannot be read from Azure or Cloudflare secret metadata. It must be issued or restored through an authorized Azure identity/certificate management path, then installed by the normal GitEdge credential UI.
- A temporary GitEdge import operation now calls a private service-binding RPC only after validating the approved profile. It retains the existing recent-human-authenticated owner route and installs data through `installSigningCredentials`, preserving owner approval and profile revision checks. Remove this operation and the binding after the authorized transfer is complete.
- Local acceptance tests exercise encrypted transfer/decryption with a synthetic source token, reject unsupported kinds and malformed recipient keys, and verify the GitEdge route rejects unsupported kinds and unapproved profiles before invoking the RPC. Production RPC, profile writes and traffic changes were not performed.
- Legacy R2 inventory was read-only: the credentials bucket has two objects (37.9 kB); the artifacts bucket has 84 objects (18.4 GB). Preserve the history bucket until the authenticated admin request status is checked and retention/data handling is separately approved.
