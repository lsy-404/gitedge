# 发现

## 当前结构与入口

- GitEdge 源码中的 `workers/auth/src/signing-keys.ts` 管理用户登记的 OpenPGP/SSH 公钥；`workers/git/src/signatures.ts` 和 `workers/git/src/api.ts` 验证 Git commit/tag 签名。这与桌面应用发布签名中心不是同一执行路径，不应因名字相同一起迁移。
- 当前桌面应用签名中心是 `lsy-404/signing-center`，默认分支内容在 commit `d1f97fb0635ab770851e0f69bfbce8a6fe10956c`。关键协调逻辑在 `src/native.ts`；请求策略/API 契约在 `src/policy.ts` 与 README 的 CI 部分。
- `src/native.ts` 的 `snapshot()` 解析 macOS/Windows 的 `public|private` lane，并从对应 executor config 固化 executor 与 policy digest；iOS 只允许 `private`。`allowed()` 再校验策略 digest、GitHub principal、build/source 仓库管理员关系、成功且精确匹配的源 workflow run；`executorRepository()` 强制 GitHub 仓库隐私属性与 snapshot lane 一致。runner 回调另校验 request generation、一次性 nonce、runner token、Actions run id、actor、workflow/ref/SHA、lease 和策略状态。
- macOS 执行器工作流：公开与私有执行器均可使用 `runner/workflow.yml`（公开镜像 `.github/workflows/macos-sign.yml`）；Windows 执行器另有 `.github/workflows/windows-sign.yml`。iOS 在私有仓的 `runner/ios-workflow.yml`。这些 workflow_dispatch 只传 request id、generation、nonce；执行客户端向中心请求输入并回传签名产物，不把输出作为 Actions artifact 发布。各工作流设置只读内容权限；Windows 另开 OIDC `id-token: write` 用于 Azure workload identity。

## 真实调用方与当前意图字段

- `lsy-404/IRIS-Build`：`scripts/submit-macos.mjs`、`scripts/import-macos.mjs` 和 `scripts/submit-windows.mjs` 都提交给 signing-center 并显式选择 `execution_visibility: 'public'`。服务端 project policy 配 source run、digest/size 和幂等键。
- `lsy-404/epilogue`：`scripts/release-signing.mjs` 显式选 `public`；服务端搜索结果显示 Epilogue Windows release 项目允许 `public_execution_allowed:false`，绑定 tag release/必需 job。
- `lsy-404/oblivionis`：`scripts/import-macos.mjs` 和 `scripts/release-signing.mjs` 显式选 `private`；桌面发布来源与签名输入走中心 API。
- 其他消费者：`SynthVCopilot/synthv-toolbox` 的 `agents_memory` 研究记录指向 signing-center 项目接入，但本次未直接核验其当前默认分支调用代码，故不列为当前已证实的生产调用路径。
- `signing-center/README.md` 说明 `execution_visibility` 支持 `auto|public|private`；`auto` 默认跟随源仓库 visibility；private source 强制检查 `public_execution_allowed` 才允许 public execution。`source_transfer` 的 `push|pull` 是独立策略：IRIS-Build 的大包已采用 push 上传到中心，Oblivionis 导入仍走 artifact pull。统一执行器并不自动意味着统一输入传输方式。

## 身份、密钥与信任边界（只记录名称/职责，不记录值）

- 中心持有 `GITHUB_TOKEN`，用以回查 run/repository 和 dispatch executor；runner workflow 使用对应仓的环境密钥 `SIGNING_RUNNER_TOKEN`。Windows 使用单独的 `SIGNING_WINDOWS_RUNNER_TOKEN`，另以 Azure OIDC 访问批准的证书 profile。Mac/iOS 的 Apple 凭据保存在中心绑定 `APPLE_CREDENTIALS`，密钥加密绑定 `APPLE_CREDENTIAL_ENCRYPTION_KEY`；iOS 凭据单独存放。密钥/证书值不读取、不复制。
- executor 配置（`src/macos-executors.json`, `src/windows-executors.json`, `src/ios-executors.json`）固定允许的 repository id、workflow 路径/ref、提交 SHA 和 token hash；macOS/Windows 分别保存 public/private 配置；iOS 仅 private。policy digest 将 executor 与产品策略绑定在 request snapshot，运行中配置更改会终止未完成请求。
- 服务对 public source 的 public execution 与 private source 的获批 public execution 分别建模；private source 默认不能送到 public executor。中心在来源运行和执行器运行的多个阶段复验仓库、run、ref、SHA、actor 和策略。改成一个 executor repo 时，需决定它的 GitHub privacy、环境保护、runner 承载方式和允许的源仓/产品集合；不能单纯删除 lane 选择并绕开 fail-closed 校验。

## 用户定案与切换决策

**已被后续用户决策取代**：保留 signing-center 并统一到 `lsy-404/signing-exec-private`。此路线不再是目标架构；对应 GitHub private-executor 切换方案已改写为 GitEdge account runner 迁移计划。

## GitEdge Account Runner signing migration (latest decision)

The latest target supersedes both the original public/private executor routing and the interim proposal to retain a separately deployed signing-center. Final architecture: GitEdge Actions owns signing admission, source/product policy, request state, scheduling, protected credential authorization, artifact transfer/verification and status APIs. The system-managed per-account private `Runner` repository supplies approved signing definitions; a dedicated GitEdge account-runner signing pool executes them. There is no permanent signing-center Worker, GitHub executor repository, proxy, or fallback. Existing GitHub source-run proof/read access may remain only for source provenance and explicitly authorized source retrieval; executor identity, credentials, leases, callbacks and result records are native GitEdge.

Runner semantics align with the account-runner repository design: one fixed-slug private `runner` repo per human in their `personal` namespace, stable user/namespace identity, owner-only; only its own personal push/manual workflows run there. Existing project CI stays in place. Ordinary workflows are under `.github/workflows/`; signing profiles use non-discovered `.gitedge/signing/<profile>.yml`, pinned by Actions policy to an immutable definition OID and explicit profile approval. Merely editing/adding YAML does not grant signing trust. Generic Actions workflow dispatch does not launch profiles from that directory. Ordinary jobs retain repository-scoped tokens; cross-repository source access is explicit and granted exact auditable resource scopes. Signing consumes a validated source archive and never checks out or executes untrusted source code.

GitEdge currently has runner registration/revocation, namespace/repository scope, queue claim, one-slot/capacity/budget scheduling, run-scoped `ge_job_` credentials, lease heartbeat/cancel, completion and local broker execution. Evidence is in baseline `7d5cdda82b97eb7accf46ac96ef326e98caa1fe9`: `packages/contracts/src/runners.ts`, `workers/actions/src/runners.ts`, `workers/actions/src/runner-scheduler.ts`, `workers/actions/src/runner-workflow.ts`, `workers/actions/src/index.ts`, `workers/actions/src/run.ts`, `workers/auth/src/index.ts`, `scripts/runner-broker.mjs`, and `scripts/actions-runner.mjs`. Current scheduling serves ordinary GitEdge Actions runs and connected GitHub webhook/JIT jobs; manual workflow dispatch is human-authenticated, runner workflow parsing discovers `.github/workflows/`, and the broker currently restricts execution to that path. The run record does not provide source-repository and trusted workflow repository/OID binding for this signing contract, nor an Actions-owned signing admission or callback assertion.

Runner labels are routing data, not authorization. The signing pool must be selected by server-authorized execution class/profile and registered pool policy; an ordinary job claiming a reserved label must never receive signing job data or credentials. Host isolation is a real current gap: `runner-broker.mjs` starts per-run child processes/directories under the broker service identity, so ordinary jobs sharing that UID can read same-UID broker state regardless of restrictive file mode. A separate profile, label, per-run directory or temporary keychain alone is insufficient. Before production keys are exposed, signing must use dedicated host/VM or a verified OS identity/security boundary that ordinary CI cannot read or escalate into. Current `localmac`/`localwin` shared CI hosts are not acceptable signing hosts absent that isolation.

The generic GitEdge Action artifact archive cap is 24 MiB (`workers/actions/src/run.ts`, `MAX_ARCHIVE_BYTES`). Existing signing-center transfers allow up to 2 GiB using 5–64 MiB multipart chunks and up to 10,000 parts, with source binding, output allowlists, digest checks, verification reports and expiring downloads. GitEdge needs a signing-only bounded streaming transfer path; do not broaden the generic artifact limit. Native `ge_job_` is a GitEdge API credential, not itself proof that a callback belongs to an approved signing profile/request/runner/lease. Add a server-validated callback/credential grant tied to native run, registered runner, lease generation, stable account/Runner identity, approved profile OID/revision, request nonce and source proof.

Credentials remain in Actions-owned protected encrypted storage, inaccessible to ordinary workflows. A trusted platform signing tool may receive the minimum short-lived material per request. Apple tools may require p12/provisioning material on the host; import only into a temporary isolated keychain/files and clean on every exit. Do not claim Apple private keys never reach the runner. Windows currently uses GitHub OIDC to access an Azure certificate profile. GitEdge has no evidenced Actions OIDC issuer/subject accepted by the tenant; validate Azure Workload Identity Federation with the tenant or use host managed identity constrained to the approved remote signing API. Do not invent a center-issued long-lived certificate substitute. Windows x64, macOS and iOS macOS ARM64 are schema/broker-routable; no live host inventory/toolchain readiness was inspected.

Callers confirmed from read-only sources: IRIS-Build (`submit-macos.mjs`, `import-macos.mjs`, `submit-windows.mjs`), Epilogue (`release-signing.mjs`) and Oblivionis (`release-signing.mjs`, `import-macos.mjs`). Remove `execution_visibility` from caller and policy contract; public and private source repositories can still submit if existing source/product admission passes, while execution always uses the private account Runner. Do not change existing project workflows beyond their signing API endpoint/credential contract, and do not fan them into Runner. Preserve explicit cross-repo authorization and source proof rules.

Feasible, but not a direct cutover. Minimum GitEdge work: Actions-owned signing API/policy/state and single signing-request metadata record bound to native `actions_runs`/`actions_runner_runs`; trusted profile admission from `.gitedge/signing/`; server-authorized signing execution class/pool; dual source and workflow identity/OID binding; signing-only exact-source grants; callback/lease attestation; bounded multipart transport and integrity verification; encrypted credential access isolated from generic workflow secret context; and host/OS isolation. Reuse mature existing signing tools and platform verification. After implementation, non-production authorization tests, platform canaries, release-request drain and history/retention reconciliation, move callers, then remove signing-center and GitHub executor workflows/tokens. No production changes, deployments, credentials, dispatches or tests were performed during this plan-only audit.
